A request, step by step, with the actual messages

MCP uses a message format called JSON-RPC. You do not need to write it, but seeing it once removes the mystery. Below is a simplified view of what happens when you ask an assistant, "Which campaigns spent over budget yesterday?" The exact fields vary by server, so treat this as a sketch.

Simplified exchange Client asks the server: tools/list
Server answers: a list such as get_campaigns (inputs: date) and get_budget (inputs: campaign_id)
Model decides: call get_campaigns with date = yesterday
Client sends: tools/call with name and arguments
Server runs it against the ad platform and returns rows
Model reads the rows and writes the answer

Two details matter for safety. First, the model only sees the tool names, the descriptions and the results. The key to the ad platform stays inside the server. Second, the tool description is text that the model reads. A badly written or hostile description can steer the model, which is why you should only run servers you trust.

SOP: Connect your first MCP server safely

SOP 4: First MCP connection Owner: you or your technical lead. Time: 1 to 2 hours

  1. Choose the data. Pick one source you read often, such as a reports folder or your analytics. Avoid anything that writes.
  2. Check the server. Who made it? Is the code open? When was it last updated? Does it ask for more access than the job needs? If you cannot answer, pick another server.
  3. Create a limited account. Make a read-only user or key just for this server. Never reuse an admin key.
  4. Install and connect. Add the server in your AI app's settings. Paste the limited key into the setting the server asks for, not into the chat.
  5. List the tools. Ask the assistant what tools the server offers. Compare with what the server's page says. Any surprise means stop.
  6. Run five real questions. Use questions whose answers you know. Check each one.
  7. Turn on approvals. Keep the setting that asks you before each tool call.
  8. Log it. Write the date, server, key name and who approved it in a simple sheet.
  9. Review in 30 days. Remove anything you did not use.
Output: one working, read-only connection with a record. Stop rule: if the server asks for write or admin access it does not need, do not install it.

SOP: Wrap your own script as an MCP server

This is the part developers enjoy. You have a script that does something useful, such as "fetch yesterday's cost from our ad account". Wrapping it as an MCP server lets any compatible assistant call it. Keep the first version tiny.

SOP 5: One-tool server Owner: developer. Time: half a day

  1. Write the function first. It takes simple inputs and returns plain data. Test it alone.
  2. Name it for the model. Use a clear name such as get_daily_cost and a one-line description that says what it returns and when to use it.
  3. Declare inputs. List each input, its type and an example. Reject anything outside the allowed values.
  4. Use the official SDK. Anthropic and others publish SDKs for common languages. Check the current docs for install steps, because they change.
  5. Keep secrets out of output. Never return keys or private fields in results.
  6. Add limits. Cap the rows returned and the calls per minute.
  7. Test with an assistant. Ask five questions that should call the tool and three that should not.
  8. Write the readme. What it does, what it can touch, what it cannot.
Output: one tool, one readme, one test list. Add a second tool only after the first has run for a week without surprises.

Tool design: small, clear, honest

  • One job per tool. "get_daily_cost" is better than "do_ad_stuff".
  • Plain names. The model picks tools by name and description, so write them like instructions to a new colleague.
  • Few tools. Ten sharp tools beat fifty vague ones. Too many choices confuse the model.
  • Safe defaults. Read before write. Dry run before real run.
  • Useful errors. Return a message that says what went wrong and what to try next.
  • Stable output. Keep the shape of results the same from call to call.

Run this before you connect anything to real data. Most failures I have seen came from skipping one of these checks, not from clever attacks.
